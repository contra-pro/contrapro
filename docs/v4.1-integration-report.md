## Data and security boundaries

Operational components never import marketing fixtures. The dashboard consumes existing authorized `rentalList` and `operationalDashboard` results. It labels counts as **displayed results**, at most 20 per follow-up group, rather than whole-agency totals. Movements exclude drafts/cancellations; vehicle counts deduplicate IDs and do not assert availability; signatures count returned follow-up states; activity represents actual latest modifications, not fabricated creations or a complete event journal. Date filters cover at most 32 UTC days and apply to movements/activity; distribution panels explicitly describe their current selection.

The new `/api/notifications` is read-only. It requires an authorized agency context and matching canonical user before calling the existing scoped overview. Each module retains restricted/error/unavailable states. It does not mark messages read, send anything, activate providers or imply an exhaustive notification inbox.

Existing authentication, RLS, validation, APIs, mutations, transactional/idempotency guarantees, history, feature gates and disabled providers remain intact. No environment file or real credential was loaded by verification. The minimal-environment verification runner inherits the existing isolation preload; telemetry is disabled. No Supabase/managed Storage/external provider was connected. No migration was applied and no feature flag was enabled. No server was started by this integration verification.
