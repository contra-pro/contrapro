## Readiness and exact prerequisites

Planning/candidate design can proceed. Native execution is **NO-GO until separately authorized**:

1. A disposable, dedicated **native PostgreSQL 17.11** target with exact server/client binary identities, private connection route and local-only binding. Existing psql is a client, not evidence of an installed server. No production VPS or managed Supabase target. Do not provision Docker/install software without explicit approval. Use an owner-provided native instance or obtain a separately scoped provisioning authorization.
2. Two isolated cluster profiles, used separately: a reviewed synthetic source baseline and an upgrade-from-recorded-0012 baseline. Fixed cluster-global role names prohibit assuming two databases in a shared cluster are isolated. Prefer independent disposable instances or separately authorized teardown/recreation; never clean an existing cluster implicitly. Initial resource estimate per active test instance: 2 vCPU, 4 GiB RAM, 10 GiB disposable storage; measure and adjust before performance claims. This is a planning estimate, not a measured application requirement.
3. A private bootstrap principal for that disposable cluster only. Model Supabase's postgres as a non-superuser administrative login with the observed attributes, rather than assuming native default superuser postgres is equivalent. Establish restricted NOLOGIN runtime/writer roles and PostgreSQL 17 ADMIN/INHERIT/SET options explicitly. Cluster-superuser setup is confined to the separately authorized bootstrap principal; application tests must use the intended restricted roles.
4. pgcrypto/uuid-ossp/plpgsql availability where required. Record other observed managed extensions separately; no need to retrieve Vault contents or activate pg_stat_statements/managed services unless the actual candidate requires them. Synthetic auth/storage schema contracts and role/grant/provider RPC stubs must be explicit and labelled; provider stubs do not prove actual managed service behavior. Real Auth records, credentials or customer data are excluded.
5. A frozen, SHA-256-pinned **executable candidate manifest** for each run, explicit predecessor schema/source checksums, expected history identifiers, role ownership and one transaction/history owner. Existing guarded drafts are source material, not release files. Keep historical 37 artifacts unchanged. Do not manufacture an applied source from object names or repair history.
6. Original deployed baseline provenance, especially 0008/0009, or an explicitly labelled candidate-baseline-only test objective. D1 confirms recorded history and catalogue families; it does not supply exact deployed SQL bodies. A candidate-only run cannot pass faithful upgrade acceptance.
7. Explicit authorization for synthetic database mutations, fixtures, role setup, test concurrency, failure injection, private evidence capture, disposable backup/restore and cleanup. The current D1 read-only authority does not include those actions. Keep external egress/providers/feature activation disabled; use an approved private credential process, no application .env loading, no secrets in argv/files/reports. TLS/CA and database/role bindings must match the isolated native target; do not reuse the managed route to run tests.

Use one dedicated session per owned migration transaction; no transaction pooler. Choose a bounded nonblocking plan advisory lock and required history/table locks per candidate. Record lock ownership/backend PID, local statement/lock/idle bounds, accepted expected duration and a process cancellation bound before native execution. Lock choices/timeouts are candidate inputs, not globally relaxed to make tests pass.
