# V4.1 authentication polish

Focused local implementation, 2026-11-26. The approved landing and dashboard were not redesigned or modified. No dependency, migration, provider activation, credential access, commit, push or deployment.

## Delivered presentation

The shared `AuthShell` extends the approved Dusk identity with the existing ContratPro C mark and wordmark, a restrained Dusk gradient, decorative orbital lines, a slow ambient effect, a refined light glass card and clear typography. Decoration is non-interactive and hidden from assistive technology. Reduced-motion mode disables the ambient animation and transitions. Auth-only selectors preserve the existing dashboard and marketing CSS.

Shared form styling provides consistent primary/secondary actions, visible input focus, contextual hints, validation summaries, error associations, disabled/unavailable messages and submission feedback. The FR/AR language selector uses real locale links with an active-language indicator. Narrow-screen spacing, logical CSS properties and Arabic typography support RTL without changing document wording.

Sign-in now reads **“Bon retour sur ContratPro”**, with **“Connectez-vous pour retrouver vos contrats et gérer votre agence.”** Sign-up uses the requested **“Créez votre compte ContratPro”** and **“Simplifiez la gestion de vos contrats de location et de vos signatures.”** Natural Arabic equivalents are provided. Provisioning/continuation uses a welcoming heading while preserving the real access status and technical/security explanation in a contextual status panel.

Password visibility buttons are native `type=button` controls with localized accessible names, `aria-controls` and `aria-pressed`. They retain only a visibility boolean, never log/store passwords, and preserve the actual native form field and POST value. New passwords still require 12–128 characters and confirmation. Unconfigured environments disable both submission and visibility controls and state their unavailability truthfully.

- `/auth/continue`, including actual provisioning and unavailable states.

- `/app/team/accept`: existing canonical identity requirement, invitation verification and feature gate retained.

Existing Supabase authentication, confirmation, password policies, sessions, provisioning, membership checks, redirect validation, rate limiting and security headers remain authoritative. No backend authentication handler/service was changed. No fake success state or newly enabled OAuth/provider path was introduced. Normal agency access/dashboard presentation remains unchanged; the new auth presentation is explicitly selected only for these journeys.
