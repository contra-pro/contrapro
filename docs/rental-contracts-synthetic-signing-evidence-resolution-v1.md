# Synthetic signing-evidence resolution V1

Status: offline-only milestone. ADR-001 remains **PROPOSED**. Production, real signing, trust establishment and Signed activation remain **NO-GO**.

## Review and boundary

Reviewed the [offline contract](rental-contracts-offline-signing-evidence-contract-v1.md), its implementation/tests and proposed [architecture](rental-contracts-electronic-signature-architecture-v1.md), [schema](rental-contracts-signing-evidence-schema-v1.md), [provider boundary](rental-contracts-signing-provider-boundary-v1.md), [threat model](rental-contracts-signing-threat-model-v1.md) and [ADR](decisions/001-proposed-electronic-signature-evidence-boundary.md).

| Question | Bounded answer |
| --- | --- |
| Reference existence | Exactly one explicit synthetic fixture descriptor for each typed evidence reference; not proof that a real evidence object exists |
| Reference consistency | Exact ID, kind, declared digest metadata/value and scope equality; no digest computation or content verification |
| Agency/contract binding | Compare every descriptor and embedded reference to the explicitly supplied context; no tenant lookup/fallback |
| Revision/artifact binding | Compare document/aggregate/attempt revisions, snapshot/manifest/renderer/party-plan metadata, final and party input/output digest claims |
| Ownership | Explicit party and subject for party records; null ownership for aggregate records; provider profile/account/environment/operation binding when applicable |
| Trust | Always unverified; identity, consent, authenticity, cryptography, trusted time and audit durability are not established |

The resolvable set is the existing typed `SigningEvidenceReference` fields: ten per party (identity, authentication, authority, consent, intent, source event, signature, time proof, time disposition and party verification), plus aggregate decision/authenticity and audit acceptance/event. Each configured provider operation adds operation/authentication references: 24 without providers, 26 with one party's provider, 28 with both. No references are generated by the resolver.

Opaque snapshot/artifact/party-plan/subject/authority/profile/account labels are compared as context metadata. They are not independently resolved into content, identities, approvals or credentials. Synthetic descriptors contain no raw proofs, personal data, timestamps, signatures or audit events. A descriptor cannot prove its declared digest; no full raw-proof schema or evidence store is invented here.

## Resolver contract

Pure synchronous `resolveSyntheticSigningEvidence(record, expectedContext, fixtureCollection)` revalidates even a previously decoded record. Context explicitly supplies the existing binding, final-artifact digest and both party input/output artifact digests. The caller supplies every descriptor; no identity, timestamp, digest or reference is generated.

Fixture collection V1 is a closed, offline-synthetic collection, limited to 128 descriptors. Each descriptor has its own V1/synthetic tag, existing typed reference, complete binding, final-artifact digest, explicit subject and nullable party input/output digests, and nullable provider binding. Null party fields apply only to aggregate records. Provider binding is required only for provider-operation/authentication kinds, and must exactly match that party's claims. These are local fixture constraints, not an operational evidence schema or provider format.

Results report status, individually resolved IDs, missing/duplicate/conflicting IDs, binding mismatches, input errors and unresolved trust dependencies. All results carry `trust: unverified` and `canActivateSigned: false`. Diagnostics expose only IDs already in the caller's validated contract, never foreign fixture values. No raw descriptors are returned.

| Status | Meaning |
| --- | --- |
| `invalid-input` | Malformed/unsupported context, collection, descriptor, reference or envelope; no lookup-completeness claim |
| `rejected` | Context disagreement, duplicates/conflicts, unexpected descriptors, ambiguous ownership or binding mismatch; any individually resolved entries remain unusable for trust |
| `incomplete` | Otherwise consistent collection with one or more missing typed references |
| `resolved-unverified` | Exactly one consistent synthetic descriptor for every typed reference, and no unexpected descriptors; never a verified signature |

Context and collection syntax are decoded first into detached frozen records, then the envelope is revalidated against the context binding. Context final/party artifact equality is checked before resolution. Descriptor binding comparisons reuse the existing validator's first rejection code; independent reference/ownership/artifact/provider mismatches are accumulated across all candidates. Diagnostics are sorted/deduplicated. Candidate comparison uses ordinary JSON serialization of exact-schema decoded descriptors to detect structural duplicates, not canonical document encoding, digest generation or cryptographic integrity.

The context and fixtures support only explicit V1 synthetic tags. Unsupported nested versions reject the entire collection; malformed extra records are not filtered out. Limits and identifier/digest syntax reuse the existing offline contract. A collection is scoped to this one supplied contract/attempt; it is not a multi-agency repository or an authorization service.

Fail closed on malformed/unsupported input, duplicate/conflicting candidates, ambiguous ownership or binding disagreement. Never choose the first/last candidate, infer owner from collection order, discard a conflicting candidate or use another agency's candidate as fallback. Unexpected fixture IDs reject the closed collection without disclosing those IDs. Empty/partial collections report missing references. Results are deterministic, including under fixture permutation; output arrays are sorted and recursively frozen. No partial result is operational evidence.

The existing always-denying trust assessment and lifecycle Signed rejection remain unchanged. No lifecycle, UI, snapshot, print/PDF or persistence integration is added.

## Unresolved dependencies and next gate

Authenticated current context and authorization, approved operational projection, lossless canonicalization/hash vectors, actual retained artifact/proof bytes, independent identity/authority/authentication verification, approved consent/intent/challenges, signature/trust/revocation/time verification, verifier authenticity, provider-profile approval, durable authorized audit commitment, retention/privacy/legal review and ADR approval remain unresolved. Matching references resolve none of these trust requirements.

**GO** for a separately scoped offline milestone specifying canonical encoding/digest conformance vectors or typed raw synthetic record schemas. These are alternative next design scopes, not approval to implement trust verification. No cryptographic algorithm/profile is selected here; approved specifications and vectors must precede any hashing implementation. **NO-GO** for real provider/authentication/capture, operational verification, Signed activation and production. ADR-001 remains PROPOSED.
