# Isolated V4.1 startup correction — 2026-11-26

## Root cause and evidence

The failure was reproduced with the original `next dev` startup, the existing credential/network preload and a minimal environment. Next 16.4.6 defaults `experimental.agentUpgrade` to `security` (`next/dist/server/config-shared.js`). During development router initialization it starts its upgrade/advisory assessment, independent of `NEXT_TELEMETRY_DISABLED=1`.

The safe opt-in fetch diagnostic identified **registry.npmjs.org** and this initiating stack:

```text
next/dist/lib/upgrade/prepare-upgrade.js:233  fetchJSON
next/dist/lib/upgrade/prepare-upgrade.js:309  readNpmAdvisories
next/dist/lib/upgrade/prepare-upgrade.js:108  getUpgradeAssessment
next/dist/lib/upgrade/nudge.js:208            assessUpgrade
next/dist/server/lib/router-server.js:180    initialize
```

The installed source defines the destination as `https://registry.npmjs.org/-/npm/v1/security/advisories/bulk`. The socket guard rejected the attempt; no host was allowed through. Throwing from the socket hook inside Undici's connection machinery terminated the development server, despite the higher-level advisory routine handling ordinary fetch rejections.

A temporary scoped `agentUpgrade:false` configuration proved that cause: both public routes then returned 200. That change alone was insufficient for manual browser review: source inspection found the development HMR connection unconditionally invokes `getVersionInfoCached()` in `hot-reloader-turbopack.js`, which calls `hot-reloader-shared-utils.js:getVersionInfo()` and requests `https://registry.npmjs.org/-/package/next/dist-tags`. This second path was identified from installed source, not exercised with a browser. The temporary advisory configuration was removed.

## Implemented fix

The manual review launcher now builds and starts the **real application in production mode**, using the existing dependencies. Development advisory assessment and HMR polling are not initialized in that mode. No fetch response is mocked, no dependency is patched, and no external hostname is whitelisted. The original socket rejection and environment-file exclusion code remain unchanged.

The launcher uses `NODE_ENV=production`, retains `NEXT_TELEMETRY_DISABLED=1`, discards inherited credentials, feature flags and Node options, and loads the same isolation preload for **both build and server**. It binds exclusively to `127.0.0.1:3330`. Each launch rebuilds current source before serving, so it cannot silently display an older build.

`A6_ISOLATED_REVIEW=1` selects regular production output in `next.config.ts`, matching `next start`. Normal builds retain the existing standalone output and normal Next defaults. This avoids Next's unsupported `next start`/standalone combination without copying assets or changing deployment configuration. The marker does not enable any business feature.

`--diagnostics` optionally logs external hostname plus initiating stack only; it does not log request paths, bodies, headers, cookies or environment values. Normal startup does not enable diagnostic logging. The socket allowlist is unchanged.

## Inspected application paths

- Root entry and locale layouts: local CSS, locale metadata and direction; no remote font loader or server fetch.
- Public `/{locale}` page: imports the marketing component only. Its route does not match the authentication proxy. Supabase configuration is not required.
- Halyard integration: original embedded CSS/system font stack, inline SVG and initials avatars. Unused original sample-data Unsplash URL strings are not rendered as image requests. No font or asset substitution was necessary.
- Startup initialization: the observed request originates in Next development utilities, not application code or a provider.
- Telemetry: already disabled in the original launcher and preload; remains disabled. Disabling telemetry alone does not suppress the development advisory/HMR requests.

No landing/UI/animation/business workflow source or approved preview file was changed by this correction.
